# 팀 10 카카오 약관 RAG 결과기·학생 평가기

이 프로젝트는 두 프로그램을 개발합니다. `result_generator/`에는 카카오 약관 질문에 답하고 근거 문서·조항을 반환하는 RAG 결과기가 있으며, `eval_generator/`에는 문항·정답 기준·익명 팀 답변을 입력받아 후보별 0~100점을 계산하는 학생 평가기를 만듭니다.

팀 번호는 **10번**입니다.

## 프로젝트 구조

```text
test/

│   ├── README.md            # RAG 결과기 상세 사용·구조 안내

│   ├── result/              # 현재 실행·제출 후보와 최신 공개 답변
│   ├── resource/            # 약관, 공개 골드, 러너, 실험 결과
│   ├── daily/               # 결과기 개발 회고
│   └── 제출용/              # 단계별 제출 보존 파일
└── eval_generator/
```

결과기와 평가기는 목적·입력·출력·외부 모델이 다르므로 코드를 서로 섞지 않고 각 폴더에서 독립적으로 관리합니다.

## 무엇을 만들었는가

결과기는 다음 계약으로 동작합니다.

```python
def answer_question(question: str) -> dict[str, object]:
    return {
        "answer": "약관 원문에 근거한 한국어 답변",
        "retrieved": [
            ["카카오계정 약관", 10],
            ["카카오 통합서비스약관", 7],
        ],
    }
```

- `answer`에는 질문에 대한 최종 답변을 반환합니다.
- `retrieved`에는 답변에 사용한 문서명과 조번호를 관련도 순으로 최대 4개 반환합니다.
- 전역 FastAPI 애플리케이션과 `GET /health`, `POST /answer`를 제공합니다.
- 생성 모델은 대회 규정에 맞는 Qwen2.5-7B-Instruct 계열을 사용합니다.
- Google Colab T4 GPU에서 외부 파일 업로드 없이 실행되는 자기완결형 노트북으로 구성했습니다.

## 무엇을 개선하려고 했는가

예선 점수는 다음 세 지표로 결정됩니다.

| 평가 항목 | 배점 | 개선 목표 |
|---|---:|---|
| 근거 순위 MRR | 20점 | 정답 문서와 조항을 retrieved 1위에 배치 |
| 핵심 내용 F1 | 30점 | 필요한 핵심 사실은 빠뜨리지 않고 불필요한 부연은 줄임 |
| 통합 LLM 평가 | 50점 | 정확성·근거성·완결성·명료성을 함께 확보 |

응답시간과 처리량은 기록되지만 예선 점수에는 직접 반영되지 않습니다. 따라서 최종 개발 단계에서는 속도보다 검색 정확도, 핵심 내용 보존, 환각 방지와 실행 안정성을 우선했습니다.

주요 개선 목표는 다음과 같습니다.

1. 질문에 맞는 최신 기준 약관과 정답 조항을 정확하게 검색합니다.
2. 복합 질문의 수치·기간·조건·예외·효력을 빠뜨리지 않습니다.
3. 원문에 없는 내용을 생성하지 않습니다.
4. 질문의 잘못된 전제에 끌려가지 않고 약관의 결론을 따릅니다.
5. 핵심 사실을 보완하되 원문 전체를 반복해 F1 정밀도를 낮추지 않습니다.
6. 공개 문항 ID를 사용하지 않고 비공개 질문에도 적용 가능한 질문·원문 기반 규칙을 사용합니다.

## 어떻게 구현했는가

전체 처리 흐름은 다음과 같습니다.

```text
내장 약관 원문
  → 조항 파싱 및 긴 조항 청킹
  → BM25 어휘 검색 + BGE-M3 의미 검색
  → Reciprocal Rank Fusion으로 순위 결합
  → 동적 Top-K 근거 선택
  → 질문 관련 원문 focus 문장 선택
  → Qwen2.5-7B-Instruct 답변 생성
  → 누락된 원문·법적 결론 제한 보완
  → 중복과 표시 형식 정리
  → answer + retrieved 반환
```

### 1. 코퍼스

운영진은 출제 기준이 되는 약관의 **이름과 기준 시행일**을 제시했고, 팀은 그 정보를 토대로 해당 시점의 정확한 약관 원문 자료를 직접 찾아 확보해야 했습니다. 현재 공식 웹페이지의 최신 내용만 사용하지 않고, 제시된 시행일과 문서 제목이 일치하는지 확인한 뒤 코퍼스를 구성했습니다.

| 운영진이 제시한 약관 이름 | 기준 시행일 | 팀이 수행한 작업 |
|---|---:|---|
| 카카오계정 약관 | 2026-05-29 | 해당 시행일의 원문을 찾아 제목·본문·조항 순서를 검증 |
| 카카오 위치정보 이용약관 | 2026-07-16 | 해당 시행일의 원문을 찾아 위치정보 관련 조항과 부칙 범위를 검증 |
| 카카오 통합서비스약관 | 2026-05-29 | 해당 시행일의 PDF 원문을 확보하고 본문을 추출·정형화 |
| 카카오 통합 약관 | 2022-08-25 | 해당 시행일의 PDF 원문을 확보하고 결과기 공식 문서명으로 매핑 |

즉, 위 네 문서는 단순히 주어진 파일을 그대로 넣은 것이 아니라 **주어진 이름과 날짜를 단서로 팀이 기준 원문을 찾고, 출제 시점과 일치하는지 확인한 자료**입니다. 확보한 원문은 메뉴·목차·클릭형 부가 콘텐츠·부칙 이후 노이즈를 제거하고 실제 약관 조항만 남겼습니다.

정제한 출제 기준 약관은 노트북 안에 내장해 제출 결과기가 로컬 경로나 Google Drive에 의존하지 않도록 했습니다.

원문은 문서명, 조번호, 제목, 본문으로 구조화합니다. 장 헤더와 부칙을 분리하고, 너무 긴 조항은 번호와 문장 경계에서 나누되 원래 문서명과 조번호를 유지합니다.

### 2. Retriever

검색은 BM25와 BGE-M3 임베딩을 함께 사용합니다.

- BM25는 질문과 원문에 같은 명사·수치·법률 표현이 있을 때 강합니다.
- Dense 검색은 표현이 달라도 의미가 비슷한 조항을 찾는 데 유리합니다.
- 두 검색 결과는 RRF로 결합해 서로 다른 점수 척도를 직접 정규화하지 않습니다.
- 같은 조항의 여러 청크는 하나로 합칩니다.
- 1위 대비 점수가 낮은 후보를 제거하는 동적 Top-K를 적용합니다.
- 선택적 CrossEncoder 리랭커 코드가 있지만 T4 메모리와 지연 비용 때문에 기본값은 비활성화했습니다.

### 3. Generator

Qwen2.5-7B-Instruct를 NF4 4-bit로 로드해 T4 GPU 메모리에 맞췄습니다. 생성은 샘플링을 끈 결정적 방식으로 실행합니다.

프롬프트에는 검색된 전체 조항과 질문에 가까운 focus 원문을 함께 전달합니다. 답변은 반드시 한국어로 작성하고, 조항의 수치·기간·법조문 번호·열거 항목을 보존하며 원문에 없는 일반론을 추가하지 않도록 지시합니다.

### 4. 누락 보완

생성 모델이 핵심 문장을 빠뜨리는 문제를 줄이기 위해 1위 검색 조항만 다시 검사합니다.

- 질문 관련성
- 기존 답변에 없는 새 정보
- 복구·효력·충돌·포함 범위 등 법적 역할
- 부정 표현과 문장 길이 위험

위 요소를 점수화하고 임계값을 넘는 원문 한 문장만 보완합니다. 전역 임계값을 무리하게 낮추지 않아 불필요한 원문이 붙는 것을 막았습니다.

실험 39에서는 다음 두 누락을 1위 원문에서 제한적으로 보완했습니다.

- 서비스 포함 범위 질문에서 제3자 제공 서비스에 가입되지 않는다는 효과
- 동의 효력 질문에서 본인의 동의가 있는 것으로 본다는 효과

문항 ID나 정답 조항 번호를 조건으로 사용하지 않고 질문 표현, 기존 답변의 누락 여부와 검색 원문을 함께 확인합니다.

### 5. 출력 정리

최종 답변은 과도한 줄바꿈과 장식용 따옴표를 제거해 자연스러운 한 문단으로 반환합니다.

실험 40에서는 한 문장 전체가 더 긴 다른 문장 안에 그대로 포함될 때 짧은 중복 문장만 제거합니다. 의미 유사도만으로 삭제하지 않고 완전 포함 관계만 사용하며, 짧은 결론은 보호합니다.

## 학생 평가기

오후 개발 단계에서는 공개 10문항, 정답 기준과 팀별 공개 답변으로 학생 평가기를 개발합니다. 3일차에는 코드를 바꾸지 않고 비공개 30문항과 `BLIND01`~`BLIND05` 익명 답변을 평가합니다.

### 고정 조건

- 판정 모델은 **Gemini 3.5 Flash만** 사용합니다.
- 문항 수·문항 번호·질문 내용을 하드코딩하지 않습니다.
- API 키는 코드나 노트북에 직접 적지 않고 Colab Secret 또는 환경변수에서 읽습니다.
- 후보 순위를 직접 만들지 않고 후보별 0~100 원점수만 저장합니다.
- 최종 파일명은 `eval_10.json`입니다.
- 최상위에는 `results` 배열만 둡니다.
- `blind_id`, `total`, `status`만 저장하며 `rank`와 `schema_version`은 저장하지 않습니다.
- 모든 문항에 유효한 수치 점수가 있으면 `completed`입니다.
- 판정 불가로 문항 점수가 하나라도 `null`이면 후보 전체를 `failed`, `total: null`로 처리합니다.
- `partial`은 모든 문항 점수를 산출할 수 있는 별도 복구 경로가 생긴 경우를 위해 유지하지만 현재 구현은 임의 대체 점수를 만들지 않습니다.
- `failed`일 때 `total`은 `null`입니다.
- 다섯 후보가 모두 존재하고 모두 `completed`여야 운영진 순위 산정에 사용됩니다.

출력 형식은 [`eval_example.json`](eval_generator/resource/eval_example.json)을 기준으로 합니다.

```json
{
  "results": [
    {
      "blind_id": "BLIND01",
      "total": 72.3147,
      "status": "completed"
    }
  ]
}
```

### 실행 규모와 예산

- 3일차 교차 평가: 5팀 × 30문항 = 150회
- 실행 방식: 순차 실행
- 팀 공용 Gemini API 한도: 19,800원
- 교차 평가 시작 전 최소 잔액: 3,000원

비용을 통제하기 위해 정답 판단에 필요한 입력만 전달하고 출력 길이를 제한합니다. 전체 재실행을 피할 수 있도록 문항별 결과를 체크포인트하되, 최종 `eval_10.json`에는 규정된 `results`만 저장합니다.

평가 논리, 프롬프트, 세부 점수 계산과 코드 구조는 자유롭게 설계할 수 있습니다. 자세한 평가기 규정과 개발 기준은 [`eval_generator/README.md`](eval_generator/README.md)를 참고합니다.

### 현재 평가기 입력 구조

```text
/content/
├── question/   # gold_questions 구조 JSON 정확히 1개, 10~50문항
├── terms/      # 카카오 약관 PDF/TXT 정확히 4개
├── blind/      # blind01.json~blind05.json
├── eval_10.ipynb
└── eval_10.json # 실행 후 생성
```

평가기는 약관 4종을 제N조 단위로 색인하고 문항별 정답 조항과 후보 `retrieved` 조항만 Gemini에 전달합니다. 배점은 MRR 10점, 핵심 내용 F1 20점, Gemini 3.5 Flash 의미 평가 70점입니다. LLM 내부는 정확성 40%, 근거성 25%, 완결성 20%, 명료성 15%이며 환각은 정확성·근거성, 반복은 명료성에서 감점합니다.

노트북은 네 셀로 나뉩니다. 셀 1은 전체 로직과 약관 캐시, 셀 2는 question 검증, 셀 3은 blind 검증, 셀 4는 실제 API 평가와 `eval_10.json` 생성을 담당합니다. 평가기는 Gemini API를 사용하므로 T4가 필요 없으며 CPU 런타임으로 충분합니다.

## Colab 실행 방법

### 결과기

1. Google Colab에서 하드웨어 가속기를 **T4 GPU**로 설정합니다.
2. `result_generator/result/result_generator_10.ipynb`를 엽니다.
3. 런타임을 새로 시작하고 위에서 아래로 실행합니다.
4. 1번 셀이 패키지 설치, 코퍼스 준비, 검색 인덱스와 Qwen 모델 로딩, FastAPI 준비를 완료할 때까지 기다립니다.
5. 2번 공통 러너가 공개 문항을 호출하고 답변 JSON을 생성하도록 실행합니다.
6. 생성된 답변과 평가 결과를 `result_generator/resource/answer/`에 보관하고 `result_generator/src/version.md`에 기록합니다.

### 평가기

1. Colab CPU 런타임을 사용합니다.
2. `/content/question`, `/content/terms`, `/content/blind`를 준비합니다.
3. Colab Secret에 `GEMINI_API_KEY`를 등록하고 노트북 액세스를 켭니다.
4. `eval_generator/eval_10.ipynb`의 셀 1~3을 실행해 모든 사전검사를 통과시킵니다.
5. API 비용이 발생하는 셀 4를 실행합니다.
6. `/content/eval_10.json`의 결과 5개가 모두 `completed`인지 확인하고 내려받습니다.


## 개발 및 실험 원칙

- 공개 문항 ID나 공개 10문항 수를 코드에 고정하지 않습니다.
- 한 실험에서는 가능한 한 핵심 변수 하나만 변경합니다.
- 사용자가 제공한 Colab 결과만 공식 측정값으로 기록합니다.
- 예상 점수는 가설로 표시하고 공식 점수와 구분합니다.
- 정확도뿐 아니라 왜 해당 기술을 선택했고 어떤 대안과 비교했는지 기록합니다.
- 실패한 실험도 원인과 회귀 문항을 남겨 같은 시도를 반복하지 않습니다.
- `result_generator/resource/cell2` 공통 러너는 팀 번호 외에 수정하지 않습니다.
- `result_generator/src/source_original.ipynb`는 수정하지 않습니다.
