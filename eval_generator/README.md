# 팀 10 카카오 약관 학생 평가기

이 폴더에는 본선 진출 5팀의 익명 답변을 채점할 학생 평가기를 구현합니다. 결과를 생성하는 RAG 코드는 `../result_generator/`에서 관리하며, 이 폴더에는 평가기 코드·평가 프롬프트·평가 실행 결과만 둡니다.

## 목적

학생 평가기는 다음 입력을 동적으로 읽습니다.

- 문항
- 문항별 정답 기준
- 팀별 또는 익명 후보별 답변 파일

각 후보의 답변 품질을 평가해 반올림하지 않은 0~100 원점수를 계산합니다. 공개 개발 단계에서는 공개 10문항과 기존 팀 답변을 사용하고, 실제 평가에서는 같은 코드로 10~50문항과 익명 후보 5팀을 처리합니다.

## 폴더 구조

```text
eval_generator/
├── README.md
├── eval_10.ipynb                 # 4개 셀로 구성된 실제 평가기
├── version.md                  # 변경·선택 이유·비교·검증 기록
├── blind/                      # 공개 10문항 시험 후보 5개
├── blind_test_mapping.md       # 시험 후보 원본 매핑, 제출 제외
├── resource/
│   ├── eval_example.json
│   ├── answers_public_*.json
│   └── practice_result_*.json
├── eval_10.json                # 로컬 출력 형식 시험 파일
└── eval_*_comparison.json      # 개발 보정 자료, 제출 제외
```

실제 제출 파일은 `eval_10.json` 하나이며 비교 JSON, 매핑 문서, 체크포인트와 문항별 상세 판정은 제출 파일에 넣지 않습니다.

현재 공개 개발 자료의 위치는 다음과 같습니다.

| 자료 | 경로 |
|---|---|
| 공개 문항·정답 기준 | `../result_generator/resource/gold_questions_public10.json` |
| 팀별 공개 답변·연습 결과 | `../result_generator/resource/answer/` |
| 평가기 출력 예시 | `resource/eval_example.json` |

3일차 입력 파일의 위치와 세부 스키마는 운영진 배포본을 직접 확인하고, 경로를 하드코딩하지 않는 동일한 로더로 처리합니다.

## 고정 조건

- 판정에는 **Gemini 3.5 Flash만** 사용합니다.
- 문항 수, 문항 번호와 질문 내용을 코드에 고정하지 않습니다.
- API 키를 코드·노트북·출력 JSON에 직접 저장하지 않습니다.
- 참가팀이 후보 순위를 계산하지 않습니다.
- 후보별 0~100 원점수만 계산합니다.
- 3일차 평가는 5팀 × 30문항, 총 150회를 순차 실행합니다.

## 출력 계약

제출 파일명은 `eval_10.json`입니다. 출력 예시는 `resource/eval_example.json`에서 확인합니다.

```json
{
  "results": [
    {
      "blind_id": "BLIND01",
      "total": 72.3147,
      "status": "completed"
    }
  ]
}
```

최상위에는 `results`만 둡니다.

| 필드 | 규칙 |
|---|---|
| `blind_id` | 운영진이 제공한 `BLIND01`~`BLIND05`를 그대로 기록 |
| `total` | 반올림하지 않은 0~100 원점수. 순위·20점 환산점수 금지 |
| `status` | 모든 문항이 유효한 수치 점수면 `completed`, 판정 불가가 하나라도 있으면 `failed` |

`failed`의 `total`은 `null`입니다. 틀린 답·핵심 누락·빈 답은 판정 가능한 오답이므로 0점까지 수치로 채점하며 `null`로 만들지 않습니다. 중국어 단독 출력, 해독 불가, API 판정 실패처럼 점수를 신뢰할 수 없는 경우만 `null`입니다. 하나라도 `null`이면 일부 문항 평균을 만들지 않고 후보 전체를 `failed`로 처리합니다. `partial`은 유효 점수를 모두 산출하는 별도 복구 경로를 위한 상태이지만 현재 구현은 임의 대체 점수를 만들지 않습니다.

`rank`, `real`, `schema_version`과 임의의 최상위 필드는 저장하지 않습니다.

다섯 후보의 중복과 누락이 없어야 하며 모두 `completed`여야 합니다. `partial`이나 `failed`가 하나라도 있으면 제출 파일 전체가 운영진 순위 산정에서 제외됩니다.

## API 키와 예산

- 팀당 공용 Gemini API 키 1개를 사용합니다.
- 총 사용 한도는 19,800원입니다.
- 3일차 교차 평가 시작 전 잔액을 최소 3,000원 남깁니다.
- API 키는 Colab Secret 또는 환경변수에서 읽습니다.
- 불필요하게 긴 입력·출력과 전체 재실행을 피합니다.

개발 중에는 문항별 응답을 별도 체크포인트에 저장해 실패 지점부터 재개할 수 있게 할 수 있습니다. 다만 최종 `eval_10.json`에는 출력 계약에 정의된 `results`만 남겨야 합니다.

## 자유 설계 영역

다음 항목은 팀이 직접 결정합니다.

- 정확성·근거성·완결성·명료성 등 평가 축
- 축별 배점과 후보 총점 계산 방식
- Gemini 프롬프트
- 실패 재시도와 파싱 검증 방식
- 코드와 노트북 구성
- 비용 절감을 위한 입력 축약과 캐싱 방식

평가기는 점수에 대한 일관된 근거를 갖되 특정 공개 문항이나 특정 팀 답변에 맞춰 설계하지 않습니다.

## 현재 `eval_10.ipynb`의 평가 방식

| 평가 항목 | 배점 | 계산 기준 |
|---|---:|---|
| MRR | 10점 | 정답 문서·조항이 `retrieved`에 처음 등장한 순위의 역수 |
| 핵심 내용 F1 | 20점 | 정답 핵심 내용과 후보 답변의 한국어 내용 토큰 정밀도·재현율 |
| Gemini 판정 | 70점 | 정확성 40%, 근거성 25%, 완결성 20%, 명료성 15%. 환각은 정확성·근거성, 중복은 명료성에서 감점 |

문항·정답 기준 JSON은 `/content/question`에 정확히 한 개만 둡니다. 이 파일은 `gold_questions`와 같은 구조이며 `questions`는 10~50개여야 합니다. 카카오 약관 4종은 `/content/terms`에 PDF 또는 TXT로 정확히 네 개 둡니다. 후보 JSON 5개는 `/content/blind`에 `blind01.json`~`blind05.json` 형태로 둡니다. 후보 내부 최상위의 어떤 변수든 값이 `BLINDxx`이면 이를 우선 사용하고, 그런 값이 없으면 파일명에서 ID를 추출합니다. 후보는 BLIND 번호 순으로 평가되며 최종 `eval_10.json`에도 `BLIND01`~`BLIND05`로 기록됩니다.

평가기에서는 약관 4종을 시작할 때 한 번 읽고 제N조 단위로 색인합니다. 각 문항의 Gemini 입력에는 전체 약관이 아니라 정답 `gold_articles`와 후보 `retrieved`에 해당하는 관련 조항만 포함합니다. 이를 통해 후보 답변이 실제 약관 원문에 근거하는지와 원문에 없는 내용을 추가했는지를 함께 판정합니다.

문항 수는 10개로 고정하지 않습니다. 골드 파일의 `questions`와 각 후보의 `answers`가 동일한 QID 집합인지 검사하므로 공개 10문항뿐 아니라 비공개 30문항과 30~50문항 입력도 같은 코드로 처리합니다.

노트북은 Gemini 호출을 문항별로 체크포인트에 기록합니다. 같은 후보 답변으로 재실행하면 완료된 판정을 재사용하지만, 답변 내용이 바뀌면 해시가 달라져 다시 평가합니다. 실제 평가 전에는 `GEMINI_API_KEY`를 Colab Secret 또는 환경변수에 등록해야 합니다.

## Colab 입력 구조

```text
/content/
├── question/
│   └── 임의이름.json       # gold_questions 구조, 정확히 1개, 10~50문항
├── terms/
│   ├── 약관1.txt 또는 pdf
│   ├── 약관2.txt 또는 pdf
│   ├── 약관3.txt 또는 pdf
│   └── 약관4.txt 또는 pdf  # 정확히 4개
├── blind/
│   ├── blind01.json
│   ├── blind02.json
│   ├── blind03.json
│   ├── blind04.json
│   └── blind05.json
└── eval_10.ipynb
```

후보 JSON 최상위의 어느 변수에든 `BLIND01`, `blind_01`, `BLIND-01` 같은 값이 있으면 그 ID를 우선합니다. 내부에 ID가 없으면 파일명에서 추출합니다. 최종 실행에서는 BLIND01~BLIND05가 정확히 한 번씩 있어야 합니다.

## 네 셀 실행 순서

### 셀 1 — 전체 로직과 약관 캐시

- `google-genai`, `pydantic`, `kiwipiepy`, `pypdf` 설치
- 모든 로더·검증·지표·Gemini 호출 함수 정의
- `/content/terms`의 PDF/TXT 네 개 로드
- 제N조 단위 색인
- `/content/.terms_index_cache.json` 저장 또는 재사용

캐시는 파일명·크기·수정 시각 지문으로 무효화됩니다. 약관 파일이 바뀌면 자동으로 다시 색인합니다.

### 셀 2 — question 사전검사

- `/content/question` 존재 확인
- JSON이 정확히 한 개인지 확인
- 문항이 10~50개인지 확인
- QID 중복, 질문, `gold_articles`, `key_facts` 검증
- 모든 정답 문서·조항이 약관 색인에 있는지 확인

### 셀 3 — blind 사전검사

- `/content/blind` 존재 확인
- BLIND01~BLIND05 누락·중복 확인
- 각 후보의 `answers`, `qid`, `retrieved`, `answer` 검증
- 후보 전체 QID와 question 전체 QID 일치 확인

이 셀까지는 Gemini 평가 비용이 발생하지 않습니다.

### 셀 4 — 실제 평가

- Gemini 3.5 Flash 문항별 순차 호출
- MRR·F1·LLM 점수 계산
- 문항별 성공 판정 체크포인트 저장
- `/content/eval_10.json` 생성

셀 1~3이 모두 성공한 뒤 셀 4를 실행합니다.

## API 키와 런타임

Colab 왼쪽의 Secrets에서 다음 이름으로 키를 등록하고 노트북 액세스를 켭니다.

```text
GEMINI_API_KEY
```

키를 코드, 출력 JSON 또는 화면 로그에 직접 적지 않습니다. 평가 모델은 API 서버에서 실행되므로 T4 GPU가 필요하지 않으며 CPU 런타임으로 충분합니다.

## 점수 계산

문항별 MRR, F1, LLM 점수를 후보 전체 문항에 평균한 뒤 다음 공식을 사용합니다.

```python
total = 10 * mean_mrr + 20 * mean_f1 + 0.7 * mean_llm
```

LLM 100점 내부 비중은 다음과 같습니다.

| 축 | 비중 | 주요 감점 |
|---|---:|---|
| 정확성 | 40% | 반대 결론, 잘못된 수치·조건·효력, 원문에 없는 주장 |
| 근거성 | 25% | 관련 조항으로 뒷받침되지 않음, 잘못된 조항 귀속, 환각 |
| 완결성 | 20% | 정답 키팩트, 조건·예외·절차·법적 효과 누락 |
| 명료성 | 15% | 모순, 불필요한 반복, 과도한 장황함, 부자연스러운 한국어 |

점수 기준점은 10점(오류·누락 없음), 7점(결론은 맞지만 중요 조건 하나 누락), 4점(일부 사실만 맞고 중요한 오류 존재), 1점(대부분 불일치), 0점(정반대·무관·전부 환각)입니다.
