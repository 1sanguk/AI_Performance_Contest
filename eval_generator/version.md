## v0.7 — 실제 후보 입력 일반화

- `answers_public_팀번호.json`, `answer_private_팀번호.json`과 그 밖의 파일명을 모두 허용합니다.
- JSON 최상위에 `answers`가 있는 파일만 후보로 인식합니다.
- 팀 번호는 내부 `team`을 우선하고, 없으면 파일명에서 추출합니다.
- 팀 번호 순으로 정렬한 후보에 `BLIND01`부터 순차 부여하며 최종 `eval_10.json`에는 실제 팀 번호나 원본 파일명을 노출하지 않습니다.
- 문항 수를 고정하지 않고 골드 QID와 후보 QID 전체 집합의 일치 여부로 검증합니다.
- `eval_10.ipynb` 첫 부분에 Colab 업로드 위치, 후보·골드 파일 조건, Gemini Secret 등록, 연습·최종 설정, 결과 검증 및 실패 주의사항을 사용법 주석으로 추가했습니다.
- 입력 경로를 `/content/question`과 `/content/blind`로 분리했습니다. `question`에는 문항·정답 기준 JSON이 정확히 한 개 있어야 하며 `blind`에는 후보 JSON 다섯 개만 둡니다.
- question의 `questions`는 10~50개로 검증하며 개수를 코드에 고정하지 않고 전부 동적으로 평가합니다.
- 후보 ID는 최상위 어느 변수에든 들어 있는 `BLINDxx` 값을 우선 사용하고, 없으면 `blindxx.json` 파일명에서 가져옵니다. 최종 실행에서는 `BLIND01`~`BLIND05`가 모두 있어야 합니다.
- `/content/terms`에 TXT/PDF 약관 4종을 받도록 추가했습니다. 약관을 제N조 단위로 색인하고 문항별 정답 조항과 후보 retrieved 조항만 Gemini 입력에 포함해 실제 원문 근거성과 환각을 판정합니다.
- 약관 전체를 문항마다 보내지 않고 관련 조항만 최대 3,500자로 제한해 API 비용과 무관 조항 혼동을 줄였습니다.
- Colab 실행 흐름을 4개 셀로 분리했습니다. 셀 1은 전체 함수 정의와 약관 색인·캐시, 셀 2는 question 1개 및 10~50문항 검증, 셀 3은 BLIND01~05와 답변 스키마 검증, 셀 4는 실제 Gemini 평가와 `eval_10.json` 생성을 담당합니다.
- 셀 1의 약관 캐시는 네 파일의 이름·크기·수정 시각 지문이 같을 때 재사용하며, 약관이 바뀌면 자동으로 다시 색인합니다.

## v0.6 — LLM 판정 척도 보정

- 정확성 40%, 근거성 25%, 완결성 20%, 명료성 15%로 변경했습니다.
- 환각과 정반대 결론은 정확성·근거성에서, 답변 중복과 불필요한 장황함은 명료성에서 감점합니다.
- 10·7·4·1·0점의 기준점을 프롬프트에 명시해 판정의 관대함과 문항별 흔들림을 줄였습니다.

## v0.5 — 최종 배점 재적용

- MRR 1.0을 10점, 키팩트 F1 1.0을 20점, LLM 100점을 70점으로 환산합니다.
- 총점 공식은 `10 × mean_mrr + 20 × mean_f1 + 0.7 × mean_llm`입니다.
- `eval_practice_comparison.json`의 `total`은 새 배점, `real`은 기존 공식 연습 배점 20·30·50의 실제 점수를 나타냅니다.

## v0.4 — 공식 연습 배점 복원

- MRR 1.0을 20점, 키팩트 F1 1.0을 30점, LLM 100점을 50점으로 환산합니다.
- 총점 공식은 `20 × mean_mrr + 30 × mean_f1 + 0.5 × mean_llm`입니다.
- 기존 practice와 동일한 원점수를 넣으면 같은 총점 척도가 나오도록 비교 파일을 다시 생성했습니다.

## v0.3 — 0점과 null 및 상태 규칙

- 정답이 없거나 사실과 다른 답변은 판정 가능한 오답이므로 0~100 사이의 수치 점수로 처리합니다. 빈 문자열 답변은 LLM 호출 없이 해당 문항의 LLM 점수를 0점으로 처리합니다.
- 한국어 없이 중국어로 출력됐거나 Gemini가 출력 손상·해독 불가로 판단한 경우에는 문항 LLM 점수를 `null`로 기록합니다.
- 한 문항이라도 LLM 점수가 `null`이면 후보의 일부 문항만 평균 내지 않고 최종 `status`를 `failed`, `total`을 `null`로 처리합니다.
- `partial`은 일부 과정이 완전하지 않더라도 모든 문항의 유효한 수치 점수를 산출할 수 있는 별도 복구 경로가 생길 경우에만 사용하도록 남겨두었습니다. 현재 구현은 임의 대체 점수를 만들지 않으므로 정상 완료는 `completed`, 하나라도 판정 불가는 `failed`입니다.
- 답변 형식 JSON 5개를 `blind_1.json`~`blind_5.json`으로 투입한 통합 시험에서 50문항을 모두 처리하고, `eval_example.json`과 같은 `results` 배열의 단일 `eval_10.json`이 생성되는 것을 확인했습니다. 통합 시험의 LLM 점수는 API 비용을 쓰지 않기 위한 모의 값이므로 품질 비교에는 사용하지 않습니다.
- 로컬 무료 모델 검증 중 생성했던 `practice/local_practice_result_5_1.json`은 제출 평가기의 산출물로 오해할 수 있어 제거했습니다. `eval_10.ipynb`는 해당 경로나 파일을 생성하지 않습니다.

## v0.2 — 공개 답변 호환성 검증

- `eval_generator/resource`의 공개 답변 36개를 실제 로더에 입력했습니다.
- 기존 구현은 한 답변의 중복 `retrieved`를 오류로 처리했지만, 평가 대상의 품질 문제 때문에 평가 실행 자체가 중단되면 제출 파일이 무효가 될 수 있어 이를 허용하도록 변경했습니다.
- MRR은 중복 여부와 관계없이 정답 근거가 최초로 등장한 순위만 사용합니다.
- 36개 답변 모두 스키마 검증을 통과했으며 MRR은 기존 `practice_result`의 값과 모두 일치했습니다.
- 무료 로컬 `gemma4:e4b`로 `answers_public_5_1.json` 10문항을 시험 평가해 상세 결과 파일을 생성했습니다. 이 모델은 Gemini 대체 제출 모델이 아니라 실행 검증용입니다.
- 로컬 시험 총점은 50.98690608799474점, 기존 practice 총점은 53.084점이었습니다. 모델과 배점이 달라 점수의 직접 일치를 성공 기준으로 삼지 않습니다.
- 현재 F1 0.40659530439973707은 기존 practice F1 0.34198과 다릅니다. MRR과 달리 기존 practice의 정확한 토큰화 규칙이 제공되지 않았으므로 이 구현은 한국어 형태소 기반 독립 F1입니다.

## v0.1 — 최초 평가기

### 무엇을 구현했는가

- `blind_1.json`부터 `blind_5.json`까지 입력 파일을 숫자 순서대로 탐색합니다.
- 파일명은 `blind_<양의 정수>.json`만 허용하며 `blind_01.json`처럼 앞에 0이 붙은 이름은 거부합니다.
- 공개 결과기와 동일한 `answers` 배열 및 `qid`, `retrieved`, `answer` 구조를 검사합니다.
- 정답 근거의 최초 검색 순위를 계산하는 MRR 10점, 핵심 내용 토큰 F1 20점, Gemini 3.5 Flash 판정 70점으로 총점을 계산합니다.
- LLM 평가는 정확성, RAG 근거 일치, 완결성, 환각 억제, 중복 억제, 명료성을 함께 판정합니다.
- 문항이나 질문 내용을 하드코딩하지 않고 정답 기준 파일의 문항을 동적으로 처리합니다.
- 문항별 판정을 체크포인트에 저장해 재실행 비용을 줄입니다.
- 최종 파일은 `eval_10.json`으로 저장하며 최상위에 `results`만 두고 순위는 기록하지 않습니다.

### 왜 이 방식을 선택했는가

MRR과 토큰 F1만으로는 근거와 반대되는 결론, 원문에 없는 설명, 같은 내용의 반복을 충분히 판별하기 어렵습니다. 따라서 객관적으로 계산 가능한 검색·내용 지표에 30점을 배정하고, 의미 수준의 품질 판단이 필요한 항목에 Gemini 평가 70점을 배정했습니다. Gemini 판정은 답변뿐 아니라 질문, 정답 기준, 후보가 반환한 검색 근거를 함께 보도록 해 RAG 근거성을 직접 확인합니다.

### 무엇과 비교했는가

- MRR 20점, F1 30점, LLM 50점인 기존 결과기 연습 평가 배점과 비교해 LLM 판정의 비중을 70점으로 높였습니다.
- 파일명이나 10개 공개 문항을 코드에 고정하는 방식 대신 입력 파일과 정답 기준을 동적으로 검사하는 방식을 선택했습니다.
- 재실행 때 150개 문항을 전부 다시 호출하는 방식 대신 후보 답변 해시 기반 체크포인트를 선택했습니다.

### 테스트 결과와 남은 검증

- 노트북 코드의 Python 문법과 출력 구조는 로컬에서 검사했습니다.
- API 키와 실제 비공개 입력이 없으므로 Gemini 호출 결과, 비용, 평가 일관성은 아직 측정하지 않았습니다.
- 공개 답변으로 소규모 시험 후 점수 분포, 재시도율, 후보 간 변별력을 기록해야 합니다.
