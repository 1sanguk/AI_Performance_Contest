# 카카오 약관 QA 결과기 개발 실험 기록

카카오 약관 QA 결과기 개발 과정에서 생성한 답변 파일과 버전별 측정 결과를 모아둔 폴더다.

- 대상: 공개 10문항 골드셋 (`gold_questions_public10.json`)
- 공식 배점: MRR 20점 + 핵심 내용 F1 30점 + LLM 판정 50점
- 이 폴더의 버전별 표는 **자체 로컬 근사 채점기**로 잰 MRR·F1 값이다.
  LLM 판정은 로컬에서 잴 수 없어 공식 채점 결과에만 포함된다.
- 모든 버전에서 MRR 1.000 (10/10 문항 1순위 적중)

> 시스템 구조와 실행 방법은 [상위 README](../README.md) 참고.
> 이 폴더는 버전별 답변 산출물과 측정 기록만 관리한다.

## 실험에서 확인한 것

### 병목은 검색이 아니라 생성

"RAG는 검색이 승부처"라는 전제로 시작했으나 MRR은 처음부터 만점이었다.
**검색된 컨텍스트만으로 낼 수 있는 최대 재현율**을 계산해보니 다음과 같았다.

| 문항 | 실제 재현율 | 컨텍스트 상한 |
|---|---:|---:|
| P07 | 0.39 | 0.96 |
| P08 | 0.39 | 0.96 |
| P02 | 0.48 | 0.90 |
| P09 | 0.53 | 0.89 |

필요한 문장은 이미 프롬프트에 다 들어가 있었고, 모델이 옮겨 적지 않았을 뿐이었다.
이 측정 하나로 청킹 최적화·리랭커 추가·top-k 조정이 무의미함이 확정되어,
이후 작업을 생성 단계에 집중할 수 있었다.

### 재현율과 정밀도는 함께 움직여야 한다

| 버전 | 재현율 | 정밀도 | F1 |
|---|---:|---:|---:|
| v12 | 0.65 | 0.75 | 0.686 |
| v14 | **0.88** | 0.49 | 0.594 |
| v16 | 0.79 | 0.70 | **0.708** |

v14에서 "관련 문장을 빠짐없이 쓰라"는 지시로 재현율은 목표를 달성했으나,
답변 뒤에 조항 원문을 통째로 덧붙이면서 정밀도가 붕괴해 F1은 오히려 하락했다.

### 프롬프트로 안 되는 것은 코드로

v15에서 "같은 내용을 두 번 쓰지 마세요"를 명시했으나 모델이 지키지 않았다(F1 0.602).
프롬프트를 포기하고 후처리 코드로 잘라낸 v16에서 0.708로 회복했다.

같은 패턴이 언어 이탈에서도 반복되었다. 7B 4bit에서 한자가 섞여 나오는 문제를
프롬프트("반드시 한국어로만")로 억제했으나 재발했고,
약관 원문·골드셋에 한자가 0개임을 확인한 뒤 **생성 단계에서 한자 토큰을 전면 차단**해 해결했다.

```python
cjk = re.compile(r"[\u3400-\u4dbf\u4e00-\u9fff\uf900-\ufaff]")
ids = list(range(tok.vocab_size))
bad_ids = [[i] for i, t in zip(ids, tok.batch_decode([[i] for i in ids])) if cjk.search(t)]
# model.generate(..., bad_words_ids=bad_ids)
```

확률적 억제가 아니라 구조적 보장이며, 정답에 한자가 없으므로 손실이 0이다.

### 측정 없이는 판단할 수 없다

한자 출력은 LLM 평가자가 지적했으나 육안으로는 찾지 못해 오탐으로 결론지었다가,
정규식 검사로 실재를 확인했다. 이후 모든 버전에 자동 검사를 적용했다.

실채점 횟수가 제한적이어서 로컬 채점기를 만들어 사용했다.
문항별 F1과 함께 **누락 토큰 / 군더더기 토큰 목록**을 출력하게 만들었고,
이것이 사실상 개선 지시서 역할을 했다.

## 최종본 구성 (v19)

| 요소 | 선택 |
|---|---|
| 원문 | 코드 내 문자열 (4종 / 72조 / 87조각) |
| 파싱 | 조 단위 + 장 메타데이터, 목차·부칙 제거 |
| 검색 | BM25(kiwipiepy 형태소) + bge-m3 임베딩, RRF 융합 |
| 생성 | Qwen2.5-7B-Instruct, 4bit(nf4), greedy |
| 언어 통제 | 한자 토큰 생성 차단 |
| 후처리 | 메타 문장·라벨·URL·유사 중복 제거 → 누락 근거 1문장 보완 |
| 근거 반환 | 검색 결과에서 직접 추출 (LLM 미경유) |

**조번호는 LLM을 거치지 않는다.** 검색 단계에서 확정된 값을 코드가 그대로 옮겨 담으므로
답변 문장과 근거 조항이 서로 다른 경로로 만들어지고, 조번호 환각이 구조적으로 불가능하다.

## 한계

공개 10문항은 튜닝에 사용한 데이터이므로 과적합 여지가 있다.
특히 근거 보완 로직의 임계값들은 특정 문항 유형을 겨냥한 성격이 있어,
**보완을 더 많이 하는 대신 확신 있을 때만 하는** 보수적 방향을 택했다.
안 붙이면 재현율만 조금 잃지만, 잘못 붙이면 정밀도와 정확성을 동시에 잃기 때문이다.

공식 채점 기준으로 남은 손실은 두 유형이다.

- **답변이 짧아 키팩트를 담지 못하는 경우** — P07은 재현율 0.00으로 F1 0.452에 그쳤다.
- **보완 문장이 길어 정밀도가 떨어지는 경우** — P09는 재현율 1.00인데 F1이 0.409다.

둘 다 개선 여지가 분명하지만, 잘 나오는 문항(P01 0.970, P08 0.955)이
함께 흔들릴 위험 대비 기대 이득이 작다고 판단해 보류했다.
